Lesson 04

Performance

JavaScript is single-threaded. One thread. One call stack. One thing at a time. Understanding this is the key to writing fast, non-blocking code. This lesson covers the call stack, the event loop, efficient DOM updates, and how the browser renders your page.

1. Introduction — Why Performance Matters

Your page has 16 milliseconds per frame to do everything — run your JavaScript, calculate styles, lay out elements, and paint pixels. That's 60 frames per second. If your JS takes longer than 16ms, the user sees jank — stuttering, freezing, unresponsive UI.

The 16ms Budget (60fps): ┌──────────────────────────────────────────────────────────┐ │ JS │ Style │ Layout │ Paint │ Composite │ └──────────────────────────────────────────────────────────┘ ←──────────── must fit in 16.6ms ────────────────────────→ If your JS alone takes 50ms: ┌────────────────────────────────────────────────────────────────────────────────┐ │ JS (50ms) ████████████████████████████████████ │ Style │ Layout │ Paint │ └────────────────────────────────────────────────────────────────────────────────┘ ←──────────── FRAME DROPPED ── user sees jank ──→

Performance in the browser comes down to two things:

  1. Don't block the main thread — keep your JS fast, use async patterns
  2. Minimize DOM work — every DOM change costs time in layout and paint

2. The Call Stack

JavaScript has one call stack. The call stack is a data structure that tracks which function is currently running and which functions called it.

🧠 Mental Model
The call stack is a stack of plates. When you call a function, a new plate goes on top. When the function returns, the plate is removed. You can only work on the top plate — the currently executing function.

How the Stack Works — Step by Step

function multiply(a, b) {
    return a * b;
}

function square(n) {
    return multiply(n, n);
}

function printSquare(n) {
    const result = square(n);
    console.log(result);
}

printSquare(4);
Call Stack execution trace: Step 1: printSquare(4) is called → pushed onto stack │ printSquare(4) │ └─────────────────┘ Step 2: printSquare calls square(4) → pushed on top │ square(4) │ │ printSquare(4) │ └─────────────────┘ Step 3: square calls multiply(4, 4) → pushed on top │ multiply(4, 4) │ │ square(4) │ │ printSquare(4) │ └─────────────────┘ Step 4: multiply returns 16 → popped off │ square(4) │ ← multiply returned 16 │ printSquare(4) │ └─────────────────┘ Step 5: square returns 16 → popped off │ printSquare(4) │ ← square returned 16 └─────────────────┘ Step 6: console.log(16) runs, printSquare returns → popped off │ │ ← stack is empty └─────────────────┘ Stack empty = JS is idle, ready for next task.

Stack Overflow — When the Stack Gets Too Full

// ❌ This will crash — infinite recursion
function forever() {
    forever();  // calls itself endlessly
}
forever();

// Error: Maximum call stack size exceeded
// (aka "Stack Overflow")
What happens: │ forever() │ │ forever() │ │ forever() │ │ forever() │ │ forever() │ │ ...×10000 │ ← browser says STOP └────────────┘ 💥 Maximum call stack size exceeded
⚠️ The Blocking Problem
While a function is on the call stack, nothing else can run. No clicks, no animations, no scrolling. The page is completely frozen. This is what "blocking the main thread" means. If your function takes 3 seconds, the page is frozen for 3 seconds. 
// ❌ This BLOCKS the page for ~3 seconds
function heavyWork() {
    let total = 0;
    for (let i = 0; i < 3_000_000_000; i++) {
        total += i;
    }
    return total;
}

heavyWork();  // 🧊 Page is FROZEN during this loop
// Can't click, can't scroll, can't type

3. The Event Loop

If JavaScript is single-threaded, how does it handle async operations like setTimeout, fetch, and event listeners without freezing? The answer is the Event Loop.

🧠 Mental Model
Think of a restaurant. The chef (call stack) can only cook one dish at a time. But the waiter (event loop) takes orders and lines them up. When the chef finishes a dish, the waiter hands them the next order. The chef never stops to wait for an oven timer — the timer is handled by kitchen helpers (Web APIs).

The Architecture

JavaScript Runtime Architecture: ┌─────────────────────┐ ┌─────────────────────────────┐ │ CALL STACK │ │ WEB APIs │ │ │ │ (provided by the browser) │ │ (one thing at │ │ │ │ a time) │────→│ • setTimeout / setInterval │ │ │ │ • fetch (network requests) │ │ │ │ • DOM events (click, etc.) │ └─────────────────────┘ │ • geolocation │ ↑ │ • requestAnimationFrame │ │ └──────────────┬───────────────┘ │ │ │ ↓ │ ┌──────────────────────────────┐ │ │ CALLBACK QUEUE │ │ │ (Task Queue) │ │ │ │ │ │ [callback1] [callback2] … │ │ └──────────────┬───────────────┘ │ │ │ ┌───────────────────────┘ │ │ ┌────┴─────────┴────┐ │ EVENT LOOP │ │ │ │ "Is the stack │ │ empty? If yes, │ │ take next │ │ callback from │ │ the queue and │ │ push it onto │ │ the stack." │ └────────────────────┘

Step-by-Step Example

console.log("1 — Start");

setTimeout(() => {
    console.log("2 — Timeout");
}, 0);  // 0ms delay!

console.log("3 — End");

// Output:
// "1 — Start"
// "3 — End"
// "2 — Timeout"
//
// Wait... WHY does "3" print before "2"?!
// The timeout is 0ms! Shouldn't it be instant?
Here's exactly what happens: Step 1: console.log("1 — Start") → runs immediately on the stack Output: "1 — Start" Step 2: setTimeout(callback, 0) → setTimeout is a Web API, not JS → The browser takes the callback and starts a 0ms timer → setTimeout itself returns immediately (stack is free) Step 3: console.log("3 — End") → runs immediately on the stack Output: "3 — End" Step 4: The 0ms timer fires → callback moves to the Callback Queue Step 5: Event Loop checks: "Is the stack empty?" → YES → Moves callback from queue to stack → callback runs: console.log("2 — Timeout") Output: "2 — Timeout"
💡 Key Insight
setTimeout(fn, 0) does NOT mean "run immediately." It means "run as soon as possible, after the current stack is clear." The callback must wait in the queue until all synchronous code finishes. Even with 0ms delay, it goes through the queue.

Microtask Queue vs Macrotask Queue

There are actually two queues, and they have different priorities:

Microtask Queue (HIGH priority)Macrotask Queue (NORMAL priority)
Promise.then() / .catch() / .finally()setTimeout()
await (after the awaited value resolves)setInterval()
queueMicrotask()requestAnimationFrame()
MutationObserverDOM events (click, input, etc.)
🧠 The Rule
After each task on the call stack finishes, the event loop drains ALL microtasks before taking the next macrotask. Microtasks always cut in line. 
console.log("1 — sync");

setTimeout(() => console.log("2 — macrotask"), 0);

Promise.resolve().then(() => console.log("3 — microtask"));

console.log("4 — sync");

// Output:
// "1 — sync"       ← call stack (runs immediately)
// "4 — sync"       ← call stack (runs immediately)
// "3 — microtask"  ← microtask queue (drained BEFORE macrotask)
// "2 — macrotask"  ← macrotask queue (runs last)
Execution order: CALL STACK MICROTASK QUEUE MACROTASK QUEUE 1. log("1") (empty) (empty) 2. setTimeout(cb) (empty) [cb: log("2")] 3. Promise.then(cb) [cb: log("3")] [cb: log("2")] 4. log("4") [cb: log("3")] [cb: log("2")] ── stack empty ── 5. Drain microtasks → log("3") 6. Next macrotask → log("2") Priority: Sync > Microtasks > Macrotasks

Tricky Interview Example

console.log("A");

setTimeout(() => console.log("B"), 0);

Promise.resolve()
    .then(() => console.log("C"))
    .then(() => console.log("D"));

console.log("E");

// Output: A, E, C, D, B
//
// A → sync (stack)
// E → sync (stack)
// C → microtask (promise .then)
// D → microtask (chained .then — added after C runs)
// B → macrotask (setTimeout)

4. setTimeout & setInterval

setTimeout — Run once after a delay

// Run callback after 2 seconds
const timerId = setTimeout(() => {
    console.log("2 seconds later");
}, 2000);

// Cancel it before it fires
clearTimeout(timerId);

setInterval — Run repeatedly

// Run every 1 second
let count = 0;
const intervalId = setInterval(() => {
    count++;
    console.log(`Tick ${count}`);
    if (count >= 5) clearInterval(intervalId);  // stop after 5
}, 1000);
⚠️ setTimeout delay is a MINIMUM, not a guarantee
setTimeout(fn, 1000) means: "After at least 1000ms, add the callback to the queue." If the call stack is busy, the callback waits. The actual delay could be 1000ms, 1050ms, or even 2000ms if the stack is blocked. 
// Proof that setTimeout delay isn't exact:
setTimeout(() => console.log("timer done"), 1000);

// This blocks the stack for 3 seconds
const start = Date.now();
while (Date.now() - start < 3000) {} // busy loop

// "timer done" prints after ~3 seconds, not 1 second
// The callback was READY at 1s, but the stack was busy until 3s

setTimeout(fn, 0) — The "Defer" Trick

// Use setTimeout(fn, 0) to defer work until after the current stack clears
// Useful for letting the browser render before continuing heavy work

btn.addEventListener("click", () => {
    btn.textContent = "Loading...";

    // Without setTimeout: browser can't repaint until ALL JS finishes
    // The user never sees "Loading..." — it jumps straight to "Done"

    setTimeout(() => {
        // Heavy work here — runs AFTER the browser repaints "Loading..."
        heavyComputation();
        btn.textContent = "Done!";
    }, 0);
});

requestAnimationFrame — The Right Way for Animations

// requestAnimationFrame runs your callback RIGHT BEFORE the next paint
// It runs at 60fps (or whatever the monitor refresh rate is)
// It PAUSES when the tab is not visible (saves battery)

let position = 0;
const box = document.querySelector(".box");

function animate() {
    position += 2;
    box.style.transform = `translateX(${position}px)`;

    if (position < 500) {
        requestAnimationFrame(animate);  // schedule next frame
    }
}

requestAnimationFrame(animate);  // start the animation
✅ Animation Rule
• Never use setTimeout / setInterval for animations — they're unreliable and waste battery.
• Always use requestAnimationFrame — it syncs perfectly with the browser's render cycle.
• Even better: use CSS transitions/animations when possible — they run on the GPU and don't block the main thread.

5. Reflow & Repaint

When you change the DOM, the browser has to recalculate how everything looks. This happens in stages:

The Browser Rendering Pipeline: JS → Style → Layout (Reflow) → Paint (Repaint) → Composite JS: Your code changes the DOM or CSSOM Style: Browser recalculates which CSS rules apply Layout: Browser calculates WHERE elements are (position, size) Paint: Browser draws pixels (colors, text, borders, shadows) Composite: Browser combines layers and puts them on screen

Reflow (Layout) — The Expensive One

A reflow happens when the browser recalculates the geometry of elements — their position and size. Reflows are expensive because changing one element can affect many others.

What triggers a reflow:

ActionWhy
Adding/removing elementsChanges the layout tree
Changing width, height, padding, marginResizes elements, shifts neighbors
Changing font-sizeChanges text flow
Changing display (none ↔ block)Adds/removes from layout
Reading offsetWidth, offsetHeightForces the browser to calculate NOW
Reading getBoundingClientRect()Forces immediate layout calculation
Window resizeEverything recalculates

Repaint — Less Expensive

A repaint happens when visual properties change but geometry stays the same (no layout change).

What triggers only a repaint (no reflow):

  • Changing color, background-color
  • Changing visibility (but not display)
  • Changing box-shadow, border-color
  • Changing outline

Composite Only — Free! (The Goal)

Some changes skip both reflow and repaint. They only trigger compositing, which is handled by the GPU:

  • transform (translate, scale, rotate)
  • opacity
  • will-change
✅ Animation Performance Rule
Only animate transform and opacity. These two properties are handled by the GPU compositor and never trigger reflow or repaint. Animating top, left, width, height causes reflow on every single frame. 
/* ❌ SLOW — triggers reflow every frame */
.box { transition: left 0.3s, top 0.3s; }

/* ✅ FAST — GPU compositing, no reflow */
.box { transition: transform 0.3s, opacity 0.3s; }

6. Add Page Content Efficiently

❌ The Worst: innerHTML += in a loop

// ❌ TERRIBLE — destroys and rebuilds ALL children on every iteration
for (let i = 0; i < 100; i++) {
    list.innerHTML += `<li>Item ${i}</li>`;
    // Each += : parse ALL HTML → destroy old nodes → create new nodes
    // → lose all event listeners → reflow → repaint
    // This happens 100 TIMES
}

❌ Bad: appendChild in a loop

// ❌ BAD — 100 separate DOM insertions = 100 potential reflows
for (let i = 0; i < 100; i++) {
    const li = document.createElement("li");
    li.textContent = `Item ${i}`;
    list.appendChild(li);  // DOM insertion — potential reflow
}

✅ Good: DocumentFragment

// ✅ GOOD — build everything in memory, one DOM insertion
const fragment = document.createDocumentFragment();

for (let i = 0; i < 100; i++) {
    const li = document.createElement("li");
    li.textContent = `Item ${i}`;
    fragment.appendChild(li);  // no reflow — fragment is in memory
}

list.appendChild(fragment);  // ONE reflow for all 100 items

✅ Good: Build a string, set innerHTML once

// ✅ GOOD — one parse, one DOM update
let html = "";
for (let i = 0; i < 100; i++) {
    html += `<li>Item ${i}</li>`;  // just building a string — no DOM yet
}
list.innerHTML = html;  // ONE DOM update

✅ Best: insertAdjacentHTML

// ✅ BEST — inserts without destroying existing content
let html = "";
for (let i = 0; i < 100; i++) {
    html += `<li>Item ${i}</li>`;
}
list.insertAdjacentHTML("beforeend", html);
// Existing children and their listeners are preserved ✅
Performance comparison (adding 1000 items): innerHTML += in loop ~800ms ████████████████████ TERRIBLE appendChild in loop ~15ms ██ ok DocumentFragment ~4ms █ great Build string + innerHTML ~3ms █ great insertAdjacentHTML ~3ms █ great + safe

7. Forced Reflow — The Hidden Performance Killer

The browser is smart — it batches DOM changes and does one reflow at the end. But if you read a layout property right after writing, the browser is forced to calculate layout immediately. This is called forced synchronous reflow (or "layout thrashing").

// ❌ LAYOUT THRASHING — read/write/read/write cycle
const boxes = document.querySelectorAll(".box");

boxes.forEach(box => {
    const width = box.offsetWidth;  // READ — forces layout calculation
    box.style.width = width + 10 + "px";  // WRITE — invalidates layout
    // Next iteration: READ again → forces ANOTHER layout calculation
    // This is called "layout thrashing" — reflow on EVERY iteration
});
// ✅ FIX — batch all reads, then batch all writes
const boxes = document.querySelectorAll(".box");

// Step 1: READ all values first
const widths = [...boxes].map(box => box.offsetWidth);

// Step 2: WRITE all values (browser batches these into one reflow)
boxes.forEach((box, i) => {
    box.style.width = widths[i] + 10 + "px";
});
💡 The Golden Rule
Batch your reads together, then batch your writes together. Never alternate between reading and writing layout properties in a loop. Read everything first, then write everything.

Properties that force reflow when read:

  • offsetWidth, offsetHeight, offsetTop, offsetLeft
  • clientWidth, clientHeight, clientTop, clientLeft
  • scrollWidth, scrollHeight, scrollTop, scrollLeft
  • getComputedStyle()
  • getBoundingClientRect()

8. Summary

The Call Stack

  • JavaScript has one call stack — one thing at a time
  • Functions are pushed when called, popped when they return
  • If the stack is busy, nothing else can run — the page freezes
  • Infinite recursion → Stack Overflow

The Event Loop

  • Async callbacks (setTimeout, events, fetch) go to Web APIs first, then to a queue
  • The event loop moves callbacks from the queue to the stack only when the stack is empty
  • Microtasks (Promises) always run before Macrotasks (setTimeout)
  • Order: Sync → Microtasks → Macrotasks

setTimeout

  • Delay is a minimum, not a guarantee
  • setTimeout(fn, 0) = "run after the current stack clears"
  • Use requestAnimationFrame for animations, not setTimeout

Reflow & Repaint

  • Reflow = recalculate geometry (size, position) — EXPENSIVE
  • Repaint = redraw pixels (color, shadow) — less expensive
  • Composite only = transform + opacity — FREE (GPU)
  • Only animate transform and opacity
