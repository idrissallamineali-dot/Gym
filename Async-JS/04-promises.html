04 — Promises

The foundation of modern async JavaScript. Promises give you a clean, composable way to represent a value that doesn't exist yet — but will, eventually.

01 — What is a Promise?

The UberEats Analogy

Imagine you're hungry. You open UberEats and place an order. The moment you tap "Order Now", the app gives you a receipt. That receipt is not the food. You can't eat it. But it's a guarantee — a promise — that the food is on its way.

Three things can happen with your order:

StatusUberEats AnalogyJavaScript
⏳ Pending Restaurant is cooking your food The async operation is still running
✅ Fulfilled Food arrived at your door! The operation succeeded — you have a value
❌ Rejected Restaurant closed. Order cancelled. The operation failed — you have an error
💡 Key Insight A Promise is a JavaScript object that represents the eventual completion (or failure) of an asynchronous operation and its resulting value. You don't have the value now, but the Promise lets you attach handlers that will run when the value is ready.

Here's the formal definition in code:

// A Promise wraps an async operation and eventually settles
const myPromise = new Promise((resolve, reject) => {
  // ...do some async work...
  // call resolve(value) on success
  // call reject(error)  on failure
});

Once a promise transitions from Pending to either Fulfilled or Rejected, it is considered settled. A settled promise cannot change state again — it's a one-way trip.

🏆 Best Practice Think of Promises as containers for future values. You don't look inside right away — you attach handlers (.then, .catch) that run when the container opens.

02 — The 3 States of a Promise

Let's look at the three possible states in detail:

StateIconMeaningProperty
pending ⏳ Initial state. Operation hasn't completed yet. No value, no error
fulfilled ✅ Operation completed successfully. [[PromiseResult]] = the resolved value
rejected ❌ Operation failed. [[PromiseResult]] = the error/reason 
// A promise that resolves after 2 seconds
const p = new Promise((resolve, reject) => {
  setTimeout(() => {
    resolve('Done!');  // state: pending → fulfilled
  }, 2000);
});

console.log(p);  // Promise {<pending>}

// 2 seconds later...
// Promise {<fulfilled>: 'Done!'}
⚠️ Important Once a promise is settled (fulfilled or rejected), its state is frozen forever. You can't change a fulfilled promise to rejected, or vice versa. Calling resolve() after reject() (or the reverse) does nothing.

03 — Creating a Promise

You create a Promise using the new Promise() constructor. It takes a single argument: an executor function. The executor receives two callbacks from the engine:

CallbackPurposeWhat it does
resolve(value) Mark the promise as fulfilled Stores the value & triggers .then() handlers
reject(error) Mark the promise as rejected Stores the error & triggers .catch() handlers 
const order = new Promise((resolve, reject) => {
  // Simulate cooking time
  setTimeout(() => {
    const isOpen = true;

    if (isOpen) {
      resolve({ dish: 'Margherita Pizza', price: 12.99 });
    } else {
      reject(new Error('Restaurant is closed'));
    }
  }, 2000);
});

console.log(order); // Promise {<pending>}

The executor runs immediately when the Promise is constructed. The setTimeout inside simulates an async delay, but the Promise object is returned right away — in its pending state.

💡 Tip The executor function runs synchronously. It's the code inside the executor (like setTimeout, fetch, etc.) that is asynchronous. The Promise itself is just a wrapper.

Helper shortcuts

Sometimes you already have the value and just want to wrap it in a Promise:

// Instantly resolved promise
const quick = Promise.resolve('Already done!');

// Instantly rejected promise
const fail = Promise.reject(new Error('Instant fail'));

04 — Consuming Promises: .then(), .catch(), .finally()

Creating a Promise is only half the story. You also need to consume it — tell JavaScript what to do when the value arrives or when an error occurs.

.then(onFulfilled)

The .then() method registers a callback that runs when the promise resolves. It receives the resolved value as its argument.

const promise = fetchUser(42);

promise.then(user => {
  console.log(user.name);  // "Alice"
});

.catch(onRejected)

The .catch() method registers a callback that runs when the promise rejects. It receives the error as its argument.

promise.catch(error => {
  console.error('Failed:', error.message);
});

.finally(onSettled)

The .finally() method runs regardless of whether the promise fulfilled or rejected. It's perfect for cleanup work — like hiding a loading spinner.

showSpinner();

fetchData()
  .then(data  => renderUI(data))
  .catch(err  => showError(err))
  .finally(() => hideSpinner());  // ← always runs!
🏆 Best Practice Always use .finally() for cleanup tasks. Loading indicators, disabling buttons, releasing resources — anything that should happen regardless of success or failure.

Here's a more complete real-world pattern:

function loadUserProfile(userId) {
  showLoadingSpinner();

  return fetch(`/api/users/${userId}`)
    .then(response => {
      if (!response.ok) throw new Error('User not found');
      return response.json();
    })
    .then(user => {
      displayProfile(user);
      return user;
    })
    .catch(error => {
      displayError(error.message);
    })
    .finally(() => {
      hideLoadingSpinner();  // runs in BOTH cases
    });
}

05 — Promise Chaining

This is the killer feature of Promises. Remember the Pyramid of Doom from the callback lesson? Promises solve it by letting you write async steps as a flat chain instead of nested callbacks.

The Golden Rule

Each .then() returns a new Promise. If you return a value from a .then(), the next .then() in the chain receives that value. If you return a Promise, the chain waits for it to settle.

getUser(1)
  .then(user    => getOrders(user.id))       // Step 1 → Step 2
  .then(orders  => getDetails(orders[0].id))  // Step 2 → Step 3
  .then(details => console.log(details))     // Step 3 → Done!
  .catch(err   => console.error(err));        // catches ANY error
💡 Key Insight The .catch() at the end will catch errors from any step in the chain. If Step 1 fails, Steps 2 and 3 are skipped and execution jumps directly to .catch(). This is vastly better than wrapping every callback in its own error handler.

Callback Hell vs. Promise Chain

❌ Callback Hell

getUser(1, (user) => {
  getOrders(user.id, (orders) => {
    getDetails(orders[0], (details) => {
      getReview(details.id, (rev) => {
        console.log(rev);
      });
    });
  });
});

✅ Promise Chain

getUser(1)
  .then(user    => getOrders(user.id))
  .then(orders  => getDetails(orders[0]))
  .then(details => getReview(details.id))
  .then(review  => console.log(review))
  .catch(err   => console.error(err));

The callback version nests deeper with every step — forming the dreaded pyramid. The Promise version stays flat. Every step is at the same indentation level. And the single .catch() handles errors for the entire chain.

06 — Promise Combinators

Sometimes you need to run multiple async operations in parallel. JavaScript gives you four powerful combinator methods for this:

MethodBehaviorUse Case
Promise.all() Waits for ALL to fulfill. Rejects if ANY fails. Loading multiple resources that are all required
Promise.race() Settles as soon as the first one settles (fulfill or reject) Timeout patterns, fastest response wins
Promise.allSettled() Waits for ALL, returns status of each (even if some fail) Fire-and-forget calls where partial success is OK
Promise.any() Resolves with the first one to succeed. Rejects only if ALL fail. Redundant sources, pick the fastest successful one

Promise.all()

const p1 = fetch('/api/user');
const p2 = fetch('/api/orders');
const p3 = fetch('/api/recommendations');

Promise.all([p1, p2, p3])
  .then(([user, orders, recs]) => {
    // ALL three resolved — render the dashboard
    renderDashboard(user, orders, recs);
  })
  .catch(err => {
    // If ANY one fails, we land here
    console.error('Dashboard failed:', err);
  });

Promise.race()

// Timeout pattern — race the fetch against a timer
const fetchData = fetch('/api/slow-endpoint');
const timeout  = new Promise((_, reject) =>
  setTimeout(() => reject(new Error('Timeout!')), 5000)
);

Promise.race([fetchData, timeout])
  .then(data => console.log('Got data:', data))
  .catch(err => console.error(err.message)); // "Timeout!"

Promise.allSettled()

Promise.allSettled([
  fetch('/api/critical'),
  fetch('/api/optional'),
  fetch('/api/analytics')
]).then(results => {
  results.forEach((r, i) => {
    if (r.status === 'fulfilled') {
      console.log(`Request ${i}: ✅`, r.value);
    } else {
      console.log(`Request ${i}: ❌`, r.reason);
    }
  });
});

Promise.any()

// Try 3 mirrors — use whichever responds first
Promise.any([
  fetch('https://cdn1.example.com/data'),
  fetch('https://cdn2.example.com/data'),
  fetch('https://cdn3.example.com/data')
]).then(fastest => {
  console.log('Fastest CDN responded!', fastest);
});
⚠️ Warning Promise.all() is "all-or-nothing". If even one promise rejects, the entire Promise.all() rejects and the successful results are lost. If you need partial results, use Promise.allSettled() instead.

07 — Common Mistakes

Promises are powerful, but there are a few traps that catch almost every developer at least once. Let's walk through the big three.

Mistake 1: Forgetting to return inside .then()

If you don't return a value from a .then(), the next .then() receives undefined. This is the #1 cause of "Why is my data undefined?"

❌ Broken — Missing return

getUser(1)
  .then(user => {
    getOrders(user.id);   // ← No return! Chain is broken
  })
  .then(orders => {
    console.log(orders);  // ← undefined 😱
  });

✅ Fixed — Return the promise

getUser(1)
  .then(user => {
    return getOrders(user.id);  // ← return it!
  })
  .then(orders => {
    console.log(orders);       // ← actual data ✅
  });
🏆 Pro Tip If your .then() only does one thing, use an arrow function with implicit return:
.then(user => getOrders(user.id))
No curly braces = automatic return. No chance of forgetting.

Mistake 2: Forgetting .catch()

If a promise rejects and there is no .catch(), you get an Unhandled Promise Rejection. In modern Node.js, this crashes your app. In browsers, you get a console error and subtle bugs.

❌ Dangerous — No error handler

fetchData()
  .then(data => process(data));
// If fetchData rejects → UNHANDLED PROMISE REJECTION 💥

✅ Safe — Always add .catch()

fetchData()
  .then(data => process(data))
  .catch(err => console.error('Failed:', err));  // ✅
⚠️ Warning Every Promise chain should end with a .catch(). This is not optional — it's a hard rule in professional codebases. Linters like ESLint can enforce this with the no-floating-promises rule.

Mistake 3: Nesting .then() inside .then()

The whole point of Promises was to escape nested callbacks. But if you nest .then() inside .then(), you're recreating the same pyramid — just with different syntax.

❌ Anti-pattern — Nested .then()

getUser(1).then(user => {
  getOrders(user.id).then(orders => {      // ← nested!
    getDetails(orders[0]).then(details => { // ← double nested!
      console.log(details);
    });
  });
});

✅ Correct — Flat chain

getUser(1)
  .then(user    => getOrders(user.id))
  .then(orders  => getDetails(orders[0]))
  .then(details => console.log(details))
  .catch(err   => console.error(err));

The flat chain is easier to read, easier to debug, and has centralized error handling. Always return and keep it flat.

08 — Error Recovery Strategies

In the Common Mistakes section, we covered what not to do. Now let's focus on what to do when things go wrong. The key insight: .catch() can recover from errors and let the chain continue.

Strategy 1: Single .catch() at the end

The simplest and most common pattern. One .catch() handles errors from any step in the chain.

fetch('/api/user')
  .then(response => response.json())
  .then(user => displayProfile(user))
  .catch(err => {
    // catches errors from ANY step above
    console.error('Failed:', err);
    showErrorPage();
  });

Strategy 2: Per-step handling with .then(success, fail)

.then() actually accepts two callbacks — the second one handles rejections only from the previous step.

fetch('/api/user')
  .then(
    response => response.json(),       // onFulfilled
    err => {                              // onRejected (fetch failure only)
      console.warn('Network error, using cache');
      return getCachedUser();            // ← recover with fallback!
    }
  )
  .then(user => displayProfile(user));

Strategy 3: .catch() that recovers

This is the most powerful pattern. A .catch() can return a value, and the chain continues as if nothing went wrong. The chain only stays broken if you throw inside .catch().

fetch('/api/primary-server')
  .catch(err => {
    console.warn('Primary failed, trying backup...');
    return fetch('/api/backup-server');  // ← recover with backup!
  })
  .then(response => response.json())
  .then(data => console.log('Got data:', data))
  .catch(err => console.error('Both failed:', err));
💡 Key Insight Think of .catch() like a catch block in try/catch. If you return a value from it, the error is "handled" and execution continues normally. If you throw (or return a rejected promise), the error propagates to the next .catch().

09 — Wrapping Legacy APIs

Not everything in JavaScript uses Promises natively. Many older APIs use callbacks or events. The skill of "promisifying" — wrapping a non-Promise API in a new Promise() — is essential for real-world development.

Pattern: Check if done → otherwise listen

When wrapping event-based APIs, always check if the thing already happened before attaching listeners. Otherwise you might miss events that fired before your listener was added.

Wrap setTimeout (timer)

function wait(ms) {
  return new Promise(resolve => {
    setTimeout(resolve, ms);
  });
}

// Usage — clean, chainable timer
wait(2000)
  .then(() => console.log('2 seconds passed!'))
  .then(() => wait(1000))
  .then(() => console.log('3 seconds total!'));

Wrap document.readyState

function domReady() {
  return new Promise(resolve => {
    // Step 1: Check if already done
    if (document.readyState === 'complete') {
      resolve();
      return;
    }

    // Step 2: Otherwise, listen for the event
    document.addEventListener('DOMContentLoaded', () => {
      resolve();
    });
  });
}

// Usage
domReady().then(() => {
  console.log('DOM is ready — safe to manipulate!');
});

Wrap XMLHttpRequest (XHR)

function get(url) {
  return new Promise((resolve, reject) => {
    const xhr = new XMLHttpRequest();
    xhr.open('GET', url);

    xhr.onload = function() {
      if (xhr.status === 200) {
        resolve(JSON.parse(xhr.response));   // ✅ success
      } else {
        reject(new Error(`HTTP ${xhr.status}`));  // ❌ HTTP error
      }
    };

    xhr.onerror = () => reject(new Error('Network Error'));
    xhr.send();
  });
}

// Usage — now it's chainable!
get('https://api.example.com/users/1')
  .then(user => console.log(user.name))
  .catch(err => console.error(err));

Wrap Image loading

function loadImage(src) {
  return new Promise((resolve, reject) => {
    const img = new Image();
    img.onload  = () => resolve(img);
    img.onerror = () => reject(new Error(`Failed to load: ${src}`));
    img.src = src;  // ← starts loading
  });
}

// Usage — load multiple images in parallel
Promise.all([
  loadImage('hero.jpg'),
  loadImage('logo.png'),
  loadImage('bg.webp')
]).then(([hero, logo, bg]) => {
  console.log('All images loaded!');
});
🏆 Universal Pattern The pattern is always the same: new Promise((resolve, reject) => { ... }). Put the old-school API call inside. Call resolve() in the success callback, reject() in the error callback. Done — now it's chainable.

10 — Array Methods & Promises

When you need to run the same async operation on every item in an array, the choice between .forEach() and .map() makes all the difference.

⚠️ The .forEach() Trap

.forEach() does NOT wait for Promises. It fires all of them and immediately moves on. You have no way to know when they finish.

❌ Broken — .forEach() doesn't wait

const urls = ['/api/user', '/api/orders', '/api/recs'];

urls.forEach(url => {
  fetch(url)
    .then(r => r.json())
    .then(data => console.log(data));
});

console.log('Done!');  // ← runs BEFORE any fetch completes! 😱

✅ The .map() + Promise.all() Solution

.map() returns an array of Promises. Feed that array into Promise.all() and you can wait for all of them.

✅ Correct — .map() + Promise.all()

const urls = ['/api/user', '/api/orders', '/api/recs'];

// .map() creates an array of Promises
const promises = urls.map(url => {
  return fetch(url).then(r => r.json());
});

// Promise.all() waits for ALL of them
Promise.all(promises)
  .then(([user, orders, recs]) => {
    console.log('All data loaded!', user, orders, recs);
  })
  .catch(err => console.error('One failed:', err));
💡 Rule of Thumb Need to run async work on an array?
.map() → creates an array of Promises
Promise.all() → waits for all of them (parallel)
.forEach() → never use with Promises. It's fire-and-forget.

Sequential vs Parallel with Arrays

The .map() + Promise.all() pattern runs everything in parallel. If you need sequential execution (one after another), use reduce() or a for...of loop with async/await (next lesson!):

// Sequential with .reduce()
const urls = ['/api/1', '/api/2', '/api/3'];

urls.reduce((chain, url) => {
  return chain.then(() => fetch(url).then(r => r.json()));
}, Promise.resolve());
// Runs: fetch /api/1 → THEN fetch /api/2 → THEN fetch /api/3

11 — Microtask Queue & Execution Order

This is the question that comes up in every JavaScript interview: why do Promise callbacks run before setTimeout callbacks, even with a 0ms delay?

Two Queues

The JavaScript event loop has two task queues, and they are not equal:

QueuePriorityWhat goes here
Microtask Queue 🥇 HIGH — drains completely before any macrotask .then(), .catch(), .finally(), queueMicrotask()
Macrotask Queue 🥈 Normal — runs one task per event loop tick setTimeout, setInterval, I/O, UI rendering

The Classic Interview Question

console.log('1. Synchronous');

setTimeout(() => {
  console.log('2. setTimeout (macrotask)');
}, 0);

Promise.resolve().then(() => {
  console.log('3. Promise .then() (microtask)');
});

console.log('4. Synchronous');

// Output order:
// 1. Synchronous
// 4. Synchronous
// 3. Promise .then() (microtask)    ← runs BEFORE setTimeout!
// 2. setTimeout (macrotask)         ← runs LAST
⚠️ Why? The event loop processes ALL microtasks before moving to the next macrotask. So even with setTimeout(fn, 0), the Promise .then() runs first because microtasks have priority.

Visual Execution Order

// Execution timeline:
//
// ┌──────────────────────────────────────────┐
// │          CALL STACK (synchronous)        │
// │  1. console.log('1. Synchronous')        │
// │  2. setTimeout → sends to MACROTASK      │
// │  3. Promise.then → sends to MICROTASK    │
// │  4. console.log('4. Synchronous')        │
// │  ─── call stack is now empty ───         │
// └──────────────────────────────────────────┘
//          ↓ drain microtask queue first
// ┌──────────────────────────────────────────┐
// │        MICROTASK QUEUE (priority!)       │
// │  → console.log('3. Promise .then()')     │
// └──────────────────────────────────────────┘
//          ↓ then macrotask queue
// ┌──────────────────────────────────────────┐
// │         MACROTASK QUEUE (normal)         │
// │  → console.log('2. setTimeout')          │
// └──────────────────────────────────────────┘
