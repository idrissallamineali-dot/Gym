03 — Callbacks & Callback Hell

Master the oldest async pattern in JavaScript — then discover why we needed something better.

1. What is a Callback?

A callback is a function that you pass as an argument to another function, with the intention that the receiving function will call it back at a later time. It's one of the most fundamental patterns in JavaScript.

Think of it this way: you call a restaurant and ask them to call you back when your table is ready. You give them your phone number (the callback), and they execute it later.

The Simplest Possible Example

// 'greet' is a callback — a function passed to another function
function greet(name) {
    console.log(`Hello, ${name}!`);
}

function processUser(name, callback) {
    // Do some work...
    callback(name);  // ← Execute the callback
}

processUser('Ali', greet);
// Output: "Hello, Ali!"JavaScript

Here, greet is the callback. We don't call it ourselves — we hand it to processUser, and it decides when to execute it.

Callbacks Are NOT Always Asynchronous

This is a critical distinction. Many people confuse "callback" with "asynchronous." They are not the same thing. A callback is simply a function passed as an argument. It can be executed synchronously (immediately) or asynchronously (later). 

// ─── Synchronous callback ───
const numbers = [1, 2, 3, 4, 5];

const doubled = numbers.map((n) => n * 2);
// The arrow function (n) => n * 2 is a callback
// But .map() calls it SYNCHRONOUSLY — right here, right now

console.log(doubled);  // [2, 4, 6, 8, 10] — already done!Synchronous
// ─── Asynchronous callback ───
setTimeout(() => {
    console.log('I run LATER!');
}, 2000);
// The arrow function is a callback
// setTimeout calls it ASYNCHRONOUSLY — after 2 seconds

console.log('I run FIRST!');Asynchronous
Method Callback Type When Executed
.map(), .filter(), .forEach() Synchronous Immediately, for each element
setTimeout(), setInterval() Asynchronous After a delay / on an interval
addEventListener() Asynchronous When the event fires
XMLHttpRequest Asynchronous When the network response arrives
💡 Key Insight Every asynchronous callback is a callback, but not every callback is asynchronous. Array methods like .map(), .filter(), and .reduce() all use synchronous callbacks.

2. Asynchronous Callbacks

Now let's focus on the async variety. Asynchronous callbacks are the original way JavaScript handled operations that take time — network requests, file reads, timers, and user events.

The pattern is always the same: you call a function and pass it a callback. The function starts some work, returns immediately, and then calls your callback when the work is done. 

console.log('1. Start');

setTimeout(() => {
    console.log('2. This runs AFTER the delay');
}, 1000);

console.log('3. This runs BEFORE the callback!');

// Output order: 1, 3, 2JavaScript

The callback inside setTimeout doesn't block. JavaScript continues running the next line immediately. When the timer expires, the event loop picks up the callback and executes it. This is the core async pattern.

Chaining Timers with Callbacks

What if you want to run timers in sequence? You nest callbacks inside callbacks. This is how sequential async operations were done before Promises: 

setTimeout(() => {
    console.log('🔴 Red light — STOP');

    setTimeout(() => {
        console.log('🟡 Yellow light — GET READY');

        setTimeout(() => {
            console.log('🟢 Green light — GO!');
        }, 2000);

    }, 2000);

}, 3000);JavaScript

Notice the nesting. Each setTimeout is inside the previous one's callback. This ensures they run in order. Try the live demo below to see this in action!

3. The Callback Pattern for Data

Beyond timers, callbacks were the standard pattern for fetching data. Before fetch() and Promises, you'd write functions that accept a callback, do some async work (like a network request), and then call the callback with the result.

Simulating an API Call

function getUser(id, callback) {
    // Simulate a 1-second network delay
    setTimeout(() => {
        const user = {
            id: id,
            name: 'Ali',
            email: 'ali@example.com'
        };
        callback(user);  // ← Hand the data to the callback
    }, 1000);
}

// Usage:
getUser(1, (user) => {
    console.log(user.name);  // "Ali" — printed after 1 second
});JavaScript

This is elegantly simple. The getUser function doesn't return the user — it calls back with the user once it's available. The caller provides a function describing what to do with the data.

A More Realistic Example

function fetchUserProfile(userId, onSuccess) {
    console.log(`⏳ Fetching profile for user #${userId}...`);

    setTimeout(() => {
        const profile = {
            id: userId,
            name: 'Sara Ahmed',
            email: 'sara@devmail.io',
            role: 'Full-Stack Developer',
            avatar: '🧑‍💻'
        };
        onSuccess(profile);
    }, 2000);
}

fetchUserProfile(42, (profile) => {
    console.log(`✅ Got: ${profile.name} (${profile.role})`);
});JavaScript

4. Error-First Callbacks

In the real world, async operations can fail. Network requests time out, files don't exist, databases crash. We need a way to communicate errors through callbacks.

The Node.js convention (also called "error-first callbacks" or "errbacks") became the universal standard. The rule is simple:

⚠️ The Error-First Rule The callback's first argument is always the error (or null if everything is fine). The second argument is the result. Always check the error before using the result! 
function getUser(id, callback) {
    setTimeout(() => {
        // Simulate: user #999 doesn't exist
        if (id === 999) {
            callback(new Error('User not found'), null);
            return;
        }

        // Success — error is null, result is the user
        callback(null, { id: id, name: 'Ali' });
    }, 1000);
}JavaScript

Consuming an Error-First Callback

// ─── Success path ───
getUser(1, (err, user) => {
    if (err) {
        console.error('❌ Error:', err.message);
        return;
    }
    console.log('✅ Got user:', user.name);
});
// Output: "✅ Got user: Ali"

// ─── Error path ───
getUser(999, (err, user) => {
    if (err) {
        console.error('❌ Error:', err.message);
        return;
    }
    console.log('✅ Got user:', user.name);
});
// Output: "❌ Error: User not found"JavaScript

This pattern works, but notice something: the same if (err) check must be repeated in every single callback. When you have nested callbacks, the error handling becomes a nightmare. Foreshadowing… 😈

5. Callback Hell — The Pyramid of Doom 🔥

This is where callbacks break down. Everything we've seen so far works beautifully when you have one or two async operations. But real applications rarely have just one.

Imagine this scenario: to display a user's shipping status, you need to do five operations in sequence, where each step depends on the result of the previous one:

  1. Get the user by ID
  2. Get the user's orders using the user's account
  3. Get the latest order's details using the order ID
  4. Get shipping status using the order's tracking number
  5. Display the result to the user

Since each step depends on the previous one, they must run sequentially. With callbacks, the only way to do this is to nest each callback inside the previous one:

The Pyramid of Doom

getUser(1, (err, user) => {
    if (err) { handleError(err); return; }

    getOrders(user.id, (err, orders) => {
        if (err) { handleError(err); return; }

        getOrderDetails(orders[0].id, (err, details) => {
            if (err) { handleError(err); return; }

            getShippingStatus(details.trackingNo, (err, status) => {
                if (err) { handleError(err); return; }

                displayResult(user, details, status);
                // We're 5 levels deep! 😱
            });
        });
    });
});The Pyramid of Doom

Look at that indentation. Each level pushes further to the right, forming a pyramid or staircase shape. This is Callback Hell.

The Three Fatal Problems

# Problem Why It Hurts
1 Unreadable Code Deep nesting makes the logic impossible to follow. Your eyes have to track indentation like a maze.
2 Error Handling Nightmare Every single level needs its own if (err) check. Miss one and errors silently disappear.
3 Impossible to Debug Stack traces become meaningless. You can't easily add logic between steps or reorder them.
⚠️ Real-World Impact Callback hell isn't just ugly code — it causes real bugs. In production codebases with 10+ levels of nesting, developers often forget error checks, creating silent failures that are almost impossible to diagnose. This was one of the biggest pain points in JavaScript before ES6.

6. Attempts to Fix Callback Hell

Developers didn't just accept callback hell — they fought back. The most common mitigation technique was extracting named functions. Instead of anonymous inline callbacks, you'd define each step as a separate named function.

Before: Nested Anonymous Callbacks

getUser(1, (err, user) => {
    if (err) { handleError(err); return; }

    getOrders(user.id, (err, orders) => {
        if (err) { handleError(err); return; }

        getOrderDetails(orders[0].id, (err, details) => {
            if (err) { handleError(err); return; }

            displayResult(user, details);
        });
    });
});Before — Nested

After: Named Functions

function onUser(err, user) {
    if (err) { handleError(err); return; }
    getOrders(user.id, onOrders);
}

function onOrders(err, orders) {
    if (err) { handleError(err); return; }
    getOrderDetails(orders[0].id, onDetails);
}

function onDetails(err, details) {
    if (err) { handleError(err); return; }
    displayResult(details);
}

// Start the chain:
getUser(1, onUser);After — Named Functions

This is flatter and more readable. Each function has a clear name that describes its purpose. But notice the problems that remain:

  • Every function still needs its own if (err) check — the error handling boilerplate is identical.
  • The flow is now scattered across multiple disconnected functions. You have to jump around the file to understand the sequence.
  • Sharing data between steps is awkward. How does onDetails access the user from step 1? You'd need closures or a shared object.
  • You cannot use try/catch to handle errors — async callbacks run in a different call stack.
⚠️ A Band-Aid, Not a Cure Named functions reduce visual nesting, but the fundamental problems remain: duplicated error handling, fragmented flow, and no way to use try/catch. We need a fundamentally different pattern.

Other Historical Attempts

Libraries like async.js (by Caolan McMahon) provided utilities like async.waterfall() and async.series() that helped manage callback flows. These were popular in the Node.js ecosystem circa 2012–2015, but they were ultimately workarounds — not solutions built into the language. 

// async.js waterfall pattern (historical)
async.waterfall([
    (cb) => getUser(1, cb),
    (user, cb) => getOrders(user.id, cb),
    (orders, cb) => getOrderDetails(orders[0].id, cb),
    (details, cb) => getShippingStatus(details.trackingNo, cb)
], (err, status) => {
    if (err) handleError(err);
    else displayResult(status);
});async.js (Historical)

This is cleaner, but still requires a third-party library and doesn't integrate with the language's native error handling (try/catch). JavaScript needed something built in.

7. The Solution Preview — Promises ✨

Everything we've seen in this lesson — the nesting, the repeated error checks, the fragmented code — was the status quo of JavaScript for years. Then, in ES6 (2015), JavaScript got a built-in solution: Promises.

Promises fundamentally change the game. Instead of passing a callback into a function, the function returns a Promise object that you can chain with .then(): 

// ─── The Promise way (preview!) ───
getUser(1)
    .then(user => getOrders(user.id))
    .then(orders => getOrderDetails(orders[0].id))
    .then(details => getShippingStatus(details.trackingNo))
    .then(status => displayResult(status))
    .catch(err => handleError(err));  // ← ONE catch for ALL errors!Preview — Promises

Look at that. Flat. Readable. One error handler for the entire chain. No pyramid. No repeated if (err) checks. This is the power of Promises.
