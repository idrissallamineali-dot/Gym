02 — The Event Loop & Call Stack

Understanding the engine room of JavaScript — how a single-threaded language handles asynchronous operations without breaking a sweat.

01. JavaScript is Single-Threaded

Before we can understand asynchronous JavaScript, we need to internalize one fundamental truth about the language:

Core Concept JavaScript has one thread of execution. It can do exactly one thing at a time. There is a single call stack, and only one piece of code is ever running at any given moment.

🍽️ The Restaurant Analogy

Imagine a restaurant with only one waiter. This single waiter is the JavaScript engine. He has to:

  • Take orders from Table 1
  • Deliver drinks to Table 4
  • Clear plates from Table 2
  • Bring the check to Table 7

He can only do one of these tasks at a time. He can't take an order and deliver drinks simultaneously — he must finish one task, then move on to the next. The tasks get queued up, and he works through them one by one.

This is exactly how JavaScript works. Your code — event handlers, function calls, DOM updates — all goes through a single thread. The engine picks up one task, executes it to completion, then picks up the next.

Wait — Then How Does Async Work? If JS is single-threaded, how can it handle timers, network requests, and user clicks at the same time? That's the big question this entire lesson answers. Spoiler: the browser provides extra threads. JS itself stays single-threaded.

Other languages like Java or C++ can spin up multiple threads to handle parallel work. JavaScript chose a simpler model: one thread + an event loop. This design avoids horrific bugs like race conditions and deadlocks — but it means we need to be smart about how we handle slow operations.

// JavaScript executes line by line, top to bottom
console.log('Line 1');   // runs first
console.log('Line 2');   // runs second
console.log('Line 3');   // runs third
// Nothing here runs in parallel. Ever.JS

02. The Call Stack

The call stack is a data structure that tracks where we are in the program. Every time you call a function, it gets pushed onto the stack. When that function finishes (returns), it gets popped off the stack.

🍽️ The Stack of Plates Analogy

Think of the call stack like a stack of plates in a cafeteria:

  • You can only add a plate to the top (push).
  • You can only remove a plate from the top (pop).
  • The plate on top is always the one currently being dealt with.

This is called LIFO — Last In, First Out. The last function pushed onto the stack is the first one to finish and get popped off.

Step-by-Step Example

Let's trace through this simple code:

function getName() {
    return 'Alice';
}

function greet() {
    const name = getName();  // calls getName()
    console.log('Hello, ' + name);
}

greet();  // calls greet()JS

Here's what happens on the call stack, step by step:

03. The Problem — Blocking Code

If JavaScript is single-threaded and can only do one thing at a time, what happens when one of those things is slow?

Imagine your code needs to:

  1. Fetch user data from a server (takes 3 seconds)
  2. Update the UI with that data
  3. Listen for button clicks

If step 1 runs synchronously (blocking the call stack for 3 seconds), then during those 3 seconds:

  • ❌ No button clicks will register
  • ❌ No animations will run
  • ❌ No scrolling will work
  • ❌ The entire page is frozen dead

This is called blocking. The slow operation blocks everything else from running because there's only one thread and it's stuck waiting.

// ⚠️ BLOCKING CODE — Never do this in real apps!
function blockFor(ms) {
    const start = Date.now();
    while (Date.now() - start < ms) {
        // Spin and do nothing — stack is locked!
    }
}

console.log('Before');
blockFor(3000);  // 😱 Page is FROZEN for 3 seconds
console.log('After');   // Only appears after 3sJS
Warning The demo below will actually freeze this page for ~3 seconds. That's the whole point — you'll feel what blocking means. Try clicking the green button while the page is frozen. It won't respond until the block ends.

04. Web APIs — The Browser's Background Helpers

Here's the key insight that makes async JavaScript possible:

The Big Secret JavaScript is single-threaded, but the browser is not! The browser provides a set of Web APIs that run on separate threads in the background. When JS needs to do something slow (timers, HTTP requests, etc.), it hands the work off to a Web API and continues running.

Think of it this way: our single waiter (JS engine) can't cook the food himself — but he can hand the order to the kitchen (Web APIs). The kitchen has its own staff working in the background. When the food is ready, the kitchen rings a bell (puts a callback in the queue), and the waiter picks it up when he's free.

How setTimeout Really Works

When you write setTimeout(fn, 2000), here's what actually happens under the hood:

  1. setTimeout(fn, 2000) gets pushed onto the call stack.
  2. JS engine sees it's a Web API call and hands the timer to the browser.
  3. setTimeout immediately pops off the call stack — JS is free to continue!
  4. The browser counts down 2 seconds in the background on a separate thread.
  5. When the timer is done, the browser puts fn into the Callback Queue.
  6. The Event Loop picks it up when the call stack is empty.
console.log('Start');

setTimeout(() => {
    console.log('Timer done!');
}, 2000);
// ^ JS hands this to the browser and moves on IMMEDIATELY

console.log('End');

// Output order:
// 'Start'       ← runs immediately
// 'End'         ← runs immediately (setTimeout didn't block!)
// 'Timer done!' ← runs after 2 secondsJS
Key Takeaway setTimeout does NOT pause JavaScript. It registers a timer with the browser and moves on. This is why "End" prints before "Timer done!" even though setTimeout appears first in the code.

05. The Callback Queue (Task Queue)

When a Web API finishes its background work — the timer expires, the fetch response arrives, the user clicks a button — the resulting callback function doesn't go directly onto the call stack. Instead, it gets placed into the Callback Queue (also called the Task Queue or Macrotask Queue).

The Callback Queue is exactly what it sounds like: a queue. It follows FIFO — First In, First Out. The first callback that finishes its Web API work is the first one that will get processed.

// Both timers finish at roughly the same time,
// but "First" entered the queue before "Second"
setTimeout(() => console.log('First'), 1000);
setTimeout(() => console.log('Second'), 1000);

// Output:
// 'First'  ← entered queue first → runs first
// 'Second' ← entered queue second → runs secondJS
Think of It Like a Line The Callback Queue is like a line at a coffee shop. Callbacks line up in the order they arrive. The Event Loop is the barista — it serves them one at a time, in order, but only when the counter (call stack) is clear.

The crucial rule is: callbacks in the queue will NEVER interrupt currently running code. Even if a timer expires while JS is in the middle of executing a function, the callback waits patiently in the queue. It will only run after the current call stack is completely empty.

setTimeout(() => console.log('Timeout!'), 0);
// ^ Even with 0ms delay, this STILL waits!

console.log('Sync code runs first');

// Output:
// 'Sync code runs first'  ← call stack must empty first
// 'Timeout!'              ← only then does the callback runJS
The Zero-Millisecond Trap setTimeout(fn, 0) does NOT mean "run immediately." It means "run as soon as the call stack is empty and the event loop gets to it." If there's a ton of synchronous code running, the 0ms callback could wait much longer than 0 milliseconds.

06. The Event Loop

Now we can put all the pieces together. The Event Loop is the orchestrator — a tiny, tireless process that connects the call stack to the callback queue.

Its algorithm is beautifully simple:

// The Event Loop (pseudocode)
while (true) {
    if (callStack.isEmpty() && callbackQueue.hasItems()) {
        const nextCallback = callbackQueue.dequeue();
        callStack.push(nextCallback);
        // Execute it!
    }
}Pseudocode

That's it. The Event Loop does ONE thing:

The Event Loop Rule "Is the call stack empty? If yes → take the first callback from the queue → push it onto the stack → let it execute." Repeat forever.

07. Microtask Queue vs. Macrotask Queue

There's one more twist. Not all callbacks are equal. JavaScript actually has two queues:

QueueAlso CalledPriorityWhat Uses It
Microtask QueueJob Queue🔴 HIGH — always runs firstPromise.then(), async/await, queueMicrotask(), MutationObserver
Macrotask QueueTask Queue / Callback Queue🟡 NORMAL — runs after microtaskssetTimeout, setInterval, setImmediate, I/O, UI rendering

The Event Loop's actual algorithm (slightly simplified) is:

  1. Execute everything on the call stack until it's empty.
  2. Process ALL microtasks in the microtask queue (drain the entire queue).
  3. Process ONE macrotask from the macrotask queue.
  4. Go back to step 2 (check for new microtasks again).
  5. Repeat forever.
The Priority Rule Microtasks always run before the next macrotask. If a Promise resolves and a setTimeout expires at the same time, the Promise's .then() callback will ALWAYS run first.

The Classic Tricky Question

This is a very common interview question. What's the output order?

console.log('1 - Synchronous');

setTimeout(() => {
    console.log('2 - setTimeout (Macrotask)');
}, 0);

Promise.resolve().then(() => {
    console.log('3 - Promise (Microtask)');
});

console.log('4 - Synchronous');JS

The output is:

// 1 - Synchronous      ← sync, runs immediately
// 4 - Synchronous      ← sync, runs immediately
// 3 - Promise (Microtask)  ← microtask, HIGH priority
// 2 - setTimeout (Macrotask)  ← macrotask, NORMAL priorityOutput

Even though setTimeout appears before the Promise in the code, and both have 0-delay, the Promise's .then() always runs first because microtasks have higher priority.

Interview Warning This microtask vs macrotask ordering is one of the most common JavaScript interview questions. Memorize the priority: Sync code → Microtasks → Macrotasks. Always.

Another Tricky Example — Nested Microtasks

Microtasks can schedule more microtasks. The event loop will drain ALL of them before moving to any macrotask:

setTimeout(() => console.log('Macro 1'), 0);

Promise.resolve()
    .then(() => {
        console.log('Micro 1');
        return Promise.resolve();
    })
    .then(() => {
        console.log('Micro 2');
    });

// Output:
// Micro 1  ← microtask first
// Micro 2  ← chained microtask, still before any macro!
// Macro 1  ← only NOW does the macrotask runJS
Mental Model Summary Think of the event loop priority like an airport boarding system:
1st class = Synchronous code (always runs first, on the stack right now).
Business class = Microtasks (Promises, queueMicrotask) — board right after 1st class.
Economy class = Macrotasks (setTimeout, setInterval) — board last.

∞ Putting It All Together

Let's recap the entire model:

  1. JavaScript is single-threaded — one call stack, one piece of code at a time.
  2. The Call Stack tracks function execution (LIFO). Functions push on when called, pop off when they return.
  3. Blocking code locks the call stack and freezes the entire page.
  4. Web APIs are browser-provided background threads that handle slow tasks (timers, network, events).
  5. The Callback Queue holds finished callbacks waiting to execute (FIFO).
  6. The Event Loop checks: "Is the stack empty? → Move next callback from queue to stack."
  7. Microtasks (Promises) have higher priority than Macrotasks (setTimeout).

This mental model is the foundation for everything we'll learn in the rest of this course — callbacks, promises, async/await — they all rely on this event loop architecture.
