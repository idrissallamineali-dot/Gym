05 — async / await

The modern, clean way to write asynchronous JavaScript. Under the hood it's still Promises — but the syntax reads like regular synchronous code.

1. The Problem with .then() Chains

In Lesson 04 you learned that Promises solve callback hell by giving us .then() chains. That was a huge improvement — but chains can still get noisy when the logic grows:

JS
fetch('/api/user/1')
  .then(response => response.json())
  .then(user => {
    return fetch(`/api/posts?userId=${user.id}`)
      .then(response => response.json())
      .then(posts => {
        return fetch(`/api/comments?postId=${posts[0].id}`)
          .then(response => response.json())
          .then(comments => {
            console.log(comments);
          });
      });
  })
  .catch(err => console.error(err));

See how each dependent request forces you deeper? You start nesting, and suddenly the pyramid of doom is almost back. The variable scoping is tricky too — user isn't available inside the innermost .then() unless you nest.

Wouldn't it be nice if we could write async code that looks like normal synchronous code?

JS — The dream
const response1 = fetch('/api/user/1');      // wait for this...
const user      = response1.json();              // then this...
const response2 = fetch(`/api/posts?userId=${user.id}`);
const posts     = response2.json();
const response3 = fetch(`/api/comments?postId=${posts[0].id}`);
const comments  = response3.json();
console.log(comments);                       // done!

That dream is exactly what async/await delivers. Let's learn the two keywords that make it happen.

2. The async Keyword

Place the word async before any function declaration and two things change:

RuleWhat it means
Always returns a PromiseEven if you return 42, the caller receives Promise.resolve(42).
Unlocks awaitInside an async function you can use the await keyword.

Syntax Variants

JS
// 1 — async function declaration
async function getUser() {
  return { name: 'Alice' };
}

// 2 — async arrow function
const getUser = async () => {
  return { name: 'Alice' };
};

// 3 — async method inside a class
class UserService {
  async fetchUser(id) {
    return { id, name: 'Alice' };
  }
}

All three forms behave identically: calling the function gives you a Promise that resolves to the returned value.

💡 Key Insight async doesn't make code run in a background thread. It simply marks a function as "I may use await inside me" and guarantees the return type is always a Promise.

Proof: the return value is always a Promise

JS
async function giveFortyTwo() {
  return 42;  // looks like a plain number...
}

const result = giveFortyTwo();
console.log(result);           // Promise {<fulfilled>: 42}
console.log(result instanceof Promise);  // true

result.then(v => console.log(v)); // 42

3. The await Keyword

await is the companion to async. Place it before any expression that returns a Promise and JavaScript will:

  1. Pause execution of that specific function until the Promise settles.
  2. Unwrap the resolved value and hand it to you as a plain variable.
  3. If the Promise rejects, throw the rejection reason as an error.
⚠ Important await does NOT block the entire program. Only the async function that contains it pauses. The rest of the page — button clicks, animations, other code — keeps running normally.

Side-by-Side Comparison

Let's rewrite the same "fetch a user" logic using both approaches so you can see the readability difference.

JS — .then() style
function loadUser() {
  fetch('/api/user/1')
    .then(res => res.json())
    .then(user => {
      console.log(user.name);
    })
    .catch(err => {
      console.error(err);
    });
}
JS — async / await style
async function loadUser() {
  try {
    const res  = await fetch('/api/user/1');
    const user = await res.json();
    console.log(user.name);
  } catch (err) {
    console.error(err);
  }
}

The async/await version reads top-to-bottom, just like synchronous code. No callbacks, no nesting — just straight-line instructions.

✅ Best Practice Think of await as saying "wait here for this value, then continue". It makes async code as easy to read as a recipe: step 1, step 2, step 3.

4. Error Handling with try...catch

With .then() chains you handle errors using .catch(). With async/await you use the standard try…catch…finally that you already know from synchronous JavaScript:

JS
async function fetchData(url) {
  try {
    const response = await fetch(url);

    if (!response.ok) {
      throw new Error(`HTTP error! Status: ${response.status}`);
    }

    const data = await response.json();
    return data;

  } catch (error) {
    // Handles BOTH network errors AND the thrown error above
    console.error('Fetch failed:', error.message);

  } finally {
    // Runs no matter what — perfect for cleanup
    hideLoadingSpinner();
  }
}

The finally block is your cleanup zone. It runs whether the request succeeds or fails — ideal for hiding spinners, resetting UI states, or closing connections.

💡 Tip If a Promise passed to await rejects, the rejection is automatically thrown as an error. You don't need to manually check — just wrap your await calls in try.

5. Sequential vs Parallel Execution

When you have multiple independent async tasks, how you await them matters enormously.

Sequential (one after another)

JS — Sequential
async function sequential() {
  const a = await task1();  // waits 1s
  const b = await task2();  // waits 1s AFTER task1
  const c = await task3();  // waits 1s AFTER task2
  // Total time: ~3 seconds
}

Each await stalls the function until the previous one resolves. The total time is the sum of all tasks.

Parallel (all at once)

JS — Parallel
async function parallel() {
  const [a, b, c] = await Promise.all([
    task1(),  // starts immediately
    task2(),  // starts immediately
    task3()   // starts immediately
  ]);
  // Total time: ~1 second (the longest task)
}

All three Promises are created before the await, so they all start at the same time. Promise.all waits until all of them resolve. Total time = the slowest task.

✅ Rule of Thumb Use sequential when each task depends on the previous result. Use parallel when the tasks are independent.

6. Top-Level await

Historically, await could only appear inside an async function. If you tried using it at the top level of a script, you'd get a syntax error.

Starting with ES2022, JavaScript modules support top-level await:

JS — module.mjs
// No wrapper function needed in an ES module!
const response = await fetch('/api/config');
const config   = await response.json();

console.log(config);

To use this feature, the file must be an ES module — either a .mjs file, or a .js file inside a project with "type": "module" in package.json, or a <script type="module"> in HTML.

⚠ Caution Top-level await blocks the loading of the entire module graph. Any module that imports your module will wait until your top-level await resolves. Use it wisely — it's great for config loading and one-time setup, but don't put long-running awaits at the top level. 
HTML
<!-- In the browser, use type="module" -->
<script type="module">
  const data = await fetch('/data.json').then(r => r.json());
  console.log(data);
</script>

7. Common Patterns

Pattern A — Looping Sequentially

Use a for...of loop when each iteration depends on the previous one, or when you want to process items one at a time:

JS
async function processSequentially(urls) {
  for (const url of urls) {
    const res  = await fetch(url);
    const data = await res.json();
    console.log(data);
  }
}
⚠ Pitfall Never use await inside .forEach(). The callback passed to forEach is a separate function and forEach doesn't wait for it. Use for...of instead.

Pattern B — Looping in Parallel

Use Promise.all with .map() when the iterations are independent:

JS
async function processInParallel(urls) {
  const results = await Promise.all(
    urls.map(async (url) => {
      const res = await fetch(url);
      return res.json();
    })
  );
  console.log(results);
}

Pattern C — IIFE for Quick Scripts

Before top-level await existed, the common workaround was an Immediately Invoked Function Expression:

JS
(async () => {
  const res  = await fetch('/api/data');
  const data = await res.json();
  console.log(data);
})();

You'll still see this pattern in codebases that need to support older environments.

8. async/await vs .then() — When to Use Which

Both approaches use Promises under the hood. Neither is "better" in an absolute sense — but each shines in different situations:

Criteria async / await .then() chains
Readability Reads like sync code — easy to follow Nesting can build up with complex logic
Error handling Standard try...catch — familiar pattern Requires .catch() or second .then() arg
Debugging Step through with debugger line by line Harder to step through chains
One-liners Requires a wrapper function Clean: fetch(url).then(r => r.json())
Parallel execution Use Promise.all() with await Use Promise.all().then()
Conditional logic Just use if/else — straightforward Conditional chains get messy
Scope access All variables are in the same scope Each .then() has its own scope
✅ Rule of Thumb Use async/await as your default for most async code — it's cleaner, easier to debug, and handles errors naturally. Use .then() for simple one-liners where you don't need the resolved value stored in a variable, or when attaching a quick handler to an existing Promise.

Example: When .then() is perfectly fine

JS
// Quick fire-and-forget — no need for async/await here
fetch('/api/analytics', { method: 'POST', body: payload })
  .then(() => console.log('Tracked!'))
  .catch(() => {}); // silently ignore errors

Example: When async/await wins

JS
async function checkout(cart) {
  try {
    const user    = await getUser();
    const address = await getShippingAddress(user.id);

    if (address.country === 'US') {
      const tax = await calculateUSTax(cart);
      cart.tax = tax;
    }

    const order = await placeOrder(cart, address);
    await sendConfirmationEmail(user.email, order.id);

    return order;
  } catch (err) {
    console.error('Checkout failed:', err);
    throw err;
  }
}

Try writing that with .then() chains — the conditional if (address.country === 'US') alone would turn the chain into a nested mess.
